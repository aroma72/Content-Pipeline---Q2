You are given the full narration (already stripped of stage directions). Check

RULE 1 — NO ASSIGNMENTS, EVER.
First-contact training content DELIVERS; it never assigns homework. FAIL any line
that hands the viewer a deliverable: "create a file", "create a <name>.md",
"your task is", "your assignment", "redo this as", "submit", "hand in", "turn in",
"complete the following", "write up and send". A closing "your turn" is allowed
ONLY as a spoken reflection prompt ("ask yourself…", "next time you…") — never a
deliverable to produce. The keep-a-human-in-the-loop / check-the-output message
must live in the video body as narration, never inside an assignment.

RULE 3 — DEFINE JARGON ON FIRST USE.
For each technical term a beginner wouldn't know (e.g. "agent", "context window",
"token", "prompt", "model", "fine-tune", "RAG", "inference"), the FIRST time it
appears it must get a plain-language definition in the same or adjacent sentence.
Calling a thing a vague nickname ("a helper") without ever naming what it actually
is also FAILS. Report each undefined-on-first-use term with the line.
A term COUNTS AS DEFINED — do NOT flag it — when a plain-language definition sits
in the SAME sentence as the term, including via an em-dash, a parenthetical, or a
"that is / meaning / which is" clause. Example that is DEFINED (do not flag):
"a feedback loop — it takes an action, checks the result, and uses that to decide
the next step." Only flag a term that is named with NO nearby explanation.

RULE 4 — NO BARE TIME-PHRASE OBJECTS.
Flag awkward dangling time phrases that drop the real object: "solves today",
"gives you every week", "handles tomorrow". The fix names the object: "solves
today's problem", "solves that same problem every week after". Report each.

RULE 6 — ONE METAPHOR PER CONCEPT.
A single concept must use ONE metaphor throughout. If the context window is called
"room to think" in one place and "memory" in another, that's a FAIL — pick one.
Report any concept given two or more competing metaphors, naming both.
IMPORTANT — do NOT over-fire this rule. A single real-world EXAMPLE or ANALOGY
used to illustrate a concept (e.g. "picture a shopkeeper who checks yesterday's
sales") is NORMAL teaching, NOT a competing metaphor. A plain mechanical
description PLUS one illustrative example is fine. Rule 6 fires ONLY when the SAME
concept is given two or more DIFFERENT sustained METAPHORS (the context window is
literally called both "a room" and "a memory"). When in doubt, do not flag.
DISTINCT concepts may each carry their OWN metaphor — that is correct teaching,
not a violation. A LIMIT and the separate PRACTICE/WORKSPACE used to manage it are
TWO concepts: e.g. the context window described as a "speedometer", AND organizing
your files described as a "house / drawing room", is two concepts with two
metaphors — do NOT flag. Only flag when ONE specific concept simultaneously wears
two metaphors (the context window itself called both "a room" and "a speedometer").
Before flagging, name the single concept and quote BOTH metaphor phrases applied to
THAT concept; if you can't, it isn't a violation.
PLAIN TECHNICAL TERMS ARE NOT METAPHORS. "context window", "working memory",
"feedback loop", "token", "prompt" are literal names for the thing — never count
them as one of the two metaphors. A ONE-OFF comparison used once to give advice
(e.g. "trim it like packing a small bag for a trip") is an analogy, NOT a sustained
metaphor — do not flag it. Only flag when ONE concept is repeatedly named as two
different FIGURATIVE things (e.g. the context window called both "a room" and "a
speedometer" across the script).
