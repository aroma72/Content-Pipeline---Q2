## 2026-09-24 — Finished videos go to TU Drive, and the volume finally drains

Branch `course-hold-2`. **Not deployed, and cannot be until a person does the one-time Drive
consent** (`node orchestrator/gdrive-auth.js`, signed in as the Taleemabad University account),
then sets `GDRIVE_REFRESH_TOKEN` + `GDRIVE_FOLDER_ID` on Railway. With those unset the code is a
no-op and behaves exactly as before.

**The ask, and what the number on screen actually was.** Aroma sent a Railway metrics screenshot
("taking too much memory") showing a ~3.2GB RAM plateau. Railway graphs RAM and does **not** graph
volume usage at all. The unbounded problem was the 50GB volume: `deliverables.persist()` copied
every `_final.mp4` there and the ONLY exit was the LMS calling `DELETE .../file`, which never
happened. Initially told Aroma the RAM plateau was a separate concern (Puppeteer+ffmpeg). **That was
wrong and lessons.md H7 already said why** — Railway's RAM metric is cgroup usage counting
file-backed pages, and `compile-lesson.js` writes ~10,800 PNGs per lesson into `frames/` that are
only cleared at the start of the NEXT render. So the working-dir sweep this change adds reduces
the RAM reading too; they are one problem, not two. Corrected to Aroma in-session. New lesson H31
draws the consequence H7 left implicit. `/health.storage` reports both numbers side by side.

**Verified, not assumed:** the `YOUTUBE_*` creds in `.env` are now the TU account and refresh
cleanly, but `tokeninfo` shows the granted scope is exactly `youtube.upload`. A Google refresh
token is scope-bound, so it can NEVER write to Drive — a second token was required regardless.
Chose a separate `GDRIVE_REFRESH_TOKEN` (same OAuth client, `drive.file` scope) over re-consenting
one token for both: one token = one failure domain, and a botched Drive consent would have taken
the working publish path down with it.

**Target folder** `UnPublished-CQ-Videos`, checked live: `canAddChildren: true`, parent is a
Shared Drive root (`0A…` id shape) — so files are Drive-owned, not person-owned. Every Drive call
needs `supportsAllDrives=true` or Shared Drive items 404 while plainly existing.

**The trap that nearly shipped a silent breakage:** `upload` runs AFTER the human review gate
(`produce → qa → review BLOCKS → approve → requeue → upload`), so it reads a `finalPath` recorded
before the wait — by which time the offload has reclaimed it. Offloading without the source ladder
in `upload.js` (render dir → volume → fetch back from Drive) would have broken publishing for
every course lesson and looked like a missing render. Temp file cleaned in a `finally`, or a
blocked upload leaks 30MB onto the disk this change exists to free.

**What must never be deleted:** `beats.js` + `durations.json`. `checkpoints.js` recomputes the
checkpoint payload and the catalogue row from them per request, so reclaiming them yields a video
that plays and cannot be answered. Reclaim is an explicit allow-list of subdirectory names
(`art frames audio clips layers out`), never `rm -rf <videoDir>` — the script sits at that dir's
top level. A test asserts the list can never contain `.`, `..` or a beats file.

**New:** `orchestrator/lib/{gdrive,video-meta,drive-offload}.js`, `orchestrator/gdrive-auth.js`,
`scripts/offload-deliverables-to-drive.js` (dry-run by default). Wired at `spine.execute`, which
now wraps `executeStages` — one hook point instead of seven `return st` sites.
338 tests green, lint clean, smoke 0 fail. Docs: SERVICE_DURABILITY §4a, DEPLOYMENT_PREREQS.

**Next session:** run the consent, then `node scripts/offload-deliverables-to-drive.js` (dry run)
to see what the volume is holding, then `--yes --limit 1` and check the file appears in Drive
before letting it loose on the rest.
